# 穗潮湾 / 手机陀螺仪 3DoF 场景优化方案

## 0. 先说结论

你当前遇到的两个问题，本质上不是两个孤立 bug，而是同一类产品约束带来的结果：

1. **交互不准确**
   不是单纯“陀螺仪不准”，而是当前 H5 原型还缺少一层专门的“姿态映射与容错层”。

2. **3D 资产摆不丰富**
   不是单纯“素材不够多”，而是 3DoF / 定点观察场景不能按自由 3D 地图那套逻辑摆物，必须换成“前方主弧区 + 分层锚点 + 声音引导 + 小范围程序变化”的布局方法。

结合当前已有文档，我判断这款游戏最适合的优化方向是：

- **输入侧**：从“alpha/beta 直接减校准值 + 线性平滑”，升级为“权限与回退 -> 四元数映射 -> 屏幕方向补偿 -> 重置中心 -> 动态死区 -> 目标锁定容错”。
- **场景侧**：不要追求自由生成式大场景，也不要把 AI 布局放到运行时；应该使用“**人工主锚点 + 轻量规则生成 + 音频与边缘提示补充丰富度**”。

这和你现有文档是对齐的：

- 世界结构是 **定点观察 / node-based 360°**。
- 玩家主要活动区应保持在 **正前方 ±90°**。
- UI 应维持 **中心准星 + 高亮 + 短提示** 的极简策略。
- 对于“找方向”的玩法，**空间音频** 本身就是核心体验增益。
- 你当前原型已经有 **拖动视角备选方案**，这部分不该删，而应该升级成正式的“精调输入”。

---

## 1. 问题一：交互不准确

### 1.1 当前问题不是“传感器坏”，而是中间层太薄

从现有原型看，当前方案大致是：

- 读 `deviceorientation`
- 只使用 `alpha / beta`
- 记录一次校准值
- 用简单的 yaw / pitch 差值去驱动画面
- 再做一次线性平滑

这套方式能快速出原型，但在手机 3DoF 游戏里会天然暴露 5 个问题：

1. **轴映射不稳**
   `alpha / beta / gamma` 是有固定旋转顺序的，直接拿差值映射相机，容易出现横竖屏切换后轴错位、抬手和转头感受不一致。

2. **缺少屏幕方向补偿**
   用户从竖屏握持、略微倾斜，到临时横过来测试，输入空间会变。

3. **缺少静止容错**
   手机静止时也会有轻微抖动，画面会持续微震。

4. **缺少目标锁定容错**
   当准星接近多个对象时，如果没有“进入阈值 / 退出阈值 / 短暂锁定”，高亮会来回跳。

5. **把“方向误差”直接暴露给玩法**
   玩家实际感受到的是“我明明差不多对准了，为什么没选中”，这既是传感器问题，也是交互判定问题。

---

### 1.2 适合当前项目的底层优化框架

这款项目不适合一上来就追求完整原始 IMU AHRS 重写。对 H5 来说，更稳的路线是：

```text
Sensor Permission
-> Orientation Mapper
-> Screen Orientation Compensation
-> Recenter / Calibration
-> Motion Filter
-> Aim Assist / Hover Hysteresis
-> Camera + Scene Interaction
```

建议拆成 5 层：

#### A. PermissionLayer：权限与回退层

职责：

- 统一处理 `DeviceOrientationEvent.requestPermission()`
- 明确区分三种状态：
  - `gyro`
  - `drag`
  - `gyro + drag fine tune`
- 权限被拒绝或设备不支持时，**自动进入拖动模式**

为什么这是第一优先：

- MDN 目前明确说明 `DeviceOrientationEvent.requestPermission()` 需要用户手势触发，且相关方向事件在很多浏览器上只在 **安全上下文（HTTPS）** 下可用。
- 你现在已经按远程服务器部署真机测试，这正好适合把陀螺仪流程做成标准链路。

对你项目的具体建议：

- “开始游戏”按钮之后先请求权限，不要页面一开就请求。
- 失败时不要报错卡死，直接切到 `drag`。
- UI 文案明确显示当前模式：
  - `陀螺仪模式`
  - `拖动模式`
  - `陀螺仪 + 手动微调`

#### B. OrientationMapper：姿态映射层

职责：

- 正确处理 `alpha / beta / gamma`
- 转成统一的内部姿态表达
- 不再直接拿 Euler 差值驱动画面

建议：

1. **内部统一使用 Quaternion**
   原因不是“为了高级”，而是因为这层本来就是姿态问题。

2. **保留游戏逻辑层的 yaw / pitch**
   也就是说：
   - 底层：Quaternion
   - 玩法层：yaw / pitch

3. **对照 Three.js DeviceOrientationControls 的成熟做法**
   社区长期使用的模式就是：
   - 先按规范顺序解释 alpha/beta/gamma
   - 再乘上一个“相机朝向修正”
   - 再乘“屏幕旋转修正”

这个模式很适合你，因为你的问题恰好集中在“手机握持方向”和“屏幕方向”。

#### C. ScreenCompensation：屏幕方向补偿层

职责：

- 监听 `screen.orientation.change`
- 屏幕方向变化后，重新修正姿态基准

对你项目的意义：

- 你虽然要求竖屏，但测试期、分享页、浏览器 UI 拉起时，用户仍然可能发生方向变化。
- 不做这一层，用户只要转一下手机，视角就可能突然歪掉。

建议：

- 方向变化时不强制重开。
- 改为：
  - 暂停 1 帧输入
  - 重算 orientation offset
  - 保留当前 scene state
  - 弹一个很轻的提示：`已重新对齐视角`

#### D. MotionFilter：动态滤波层

职责：

- 去掉静止抖动
- 保持快速移动时仍然跟手
- 避免“越平滑越迟钝”

最适合你的不是重滤波，而是 **分状态滤波**：

1. **静止状态**
   - 更强平滑
   - 死区更大
   - 允许缓慢纠偏

2. **正常观察状态**
   - 中等平滑
   - 小死区

3. **快速转向状态**
   - 降低平滑
   - 优先响应速度

推荐策略：

- yaw / pitch 变化很小时，进入死区，不更新视角
- 连续多帧都非常小，进入静止状态
- 静止状态下缓慢更新基线，抵消小漂移
- 一旦速度明显上升，立即切回快速响应

也就是说，不是固定 `0.18` 之类的常数，而是：

```text
低速 = 稳
中速 = 顺
高速 = 跟手
```

#### E. AimAssist：准星判定容错层

这是最容易被忽略，但对“手感”提升最大的部分。

建议加入：

1. **进入阈值 > 退出阈值**
   例如：
   - 进入高亮：12°
   - 退出高亮：9°

   这样对象不会在边缘反复闪跳。

2. **短时锁定**
   目标一旦成为当前 hover，至少保留 `120ms ~ 180ms` 再允许切换。

3. **对象优先级**
   当多个对象接近时：

```text
交互对象 > 装饰对象
任务对象 > 非任务对象
当前屏幕中心更近者 > 边缘对象
前景对象 > 中景对象
```

4. **动态命中角**
   不同对象的 `interactAngle` 不该一刀切：

- 小鸡：大一些
- 鸡蛋：中等
- 料斗 / 食槽：可略大
- 集市公告板：大
- 装饰物：不参与

5. **边缘辅助**
   当对象在视野边缘附近时，不要等它完整进中间再提示，可先给弱提示：
   - 边缘箭头
   - 轻高亮
   - 短促方向音

这部分和你现有文档里的“极简 UI + 方向提示 + 空间音频”高度一致。

---

### 1.3 这款游戏最值得做的输入方案，不是“绝对北”，而是“相对中心”

这是非常关键的一点。

对鸡舍、码头、果园、集市这种生活场景来说，玩家不关心“世界北方”在哪里，只关心：

```text
我当前面向哪里
相对于开局正前方，我现在左转了多少 / 右转了多少
```

因此建议：

- **默认使用相对朝向**
- 不要把“绝对地磁北”当成主要基准

原因：

1. 室内和码头边环境都可能有磁干扰。
2. 地磁虽然能修 yaw 漂移，但在手机 H5 里并不总是比“频繁重置中心”更稳定。
3. 你的玩法不是导航，不需要真实朝北。

更合适的产品逻辑是：

- 用户进入场景时按一次“开始 / 居中”
- 当前朝向记为 `0°`
- 后续所有对象都按相对 yaw 参与判定
- 允许随时一键“重新居中”

如果未来做原生 App、Unity 或 WebXR 再考虑更完整的 AHRS / 磁力计校准。

---

### 1.4 对 H5 当前阶段的优先级建议

#### P0：必须先做

1. `requestPermission + fallback drag`
2. Quaternion 映射
3. 屏幕方向补偿
4. 一键重置中心
5. 进入 / 退出阈值 + hover 锁定
6. 静止死区
7. 陀螺仪与拖动共存

其中第 7 点很重要：

- 陀螺仪负责主视角
- 拖动负责细调偏移

这比“要么纯陀螺仪，要么纯拖动”更适合你当前测试与真实玩家体验。

#### P1：推荐做

1. 加入 `devicemotion` 的运动强度判断，做动态平滑
2. 静止时估算局部偏移，减少微漂
3. 为四个场景分别配置不同的 `interactAngle`
4. 为小鸡 / 鸡蛋加更明显的边缘提示

#### P2：后续再做

1. 原生传感器融合（Madgwick / Mahony / x-io Fusion）
2. 预测性插值
3. 更细的姿态置信度评分

这类方案在 GitHub 和 x-io 社区非常成熟，但更适合 **可拿到更完整原始传感器数据** 的原生环境，不建议现在就在 H5 里重实现一整套 AHRS。

## 2. 问题二：3D 资产如何摆，才能既丰富又不乱

### 2.1 你这个项目不适合“自由大世界摆法”

原因非常直接：

- 这是 **定点观察**
- 玩家主要活动范围在 **前方 ±90°**
- 场景重点是 **看向 -> 高亮 -> 点击 / 长按**
- 玩家不能自由走近远处物体

所以这里的“丰富度”不来自于“大地图”，而来自于：

1. 视野前弧区的层次感
2. 侧向发现点
3. 声音与动效提示
4. 小规模变化而不是全随机生成

换句话说：

**你的目标不是做一个大而自由的 3D 场景，而是做一个“转头时一直有东西看、对准时一直有反馈、每个方向都有一点故事感”的观察型空间。**

---

### 2.2 最适合你的布局结构：主锚点 + 深度带 + 规则簇

建议将每个场景对象分成 4 类锚点：

#### A. Structural Anchor：结构锚点

负责场景骨架，不参与交互。

例如：

- 鸡舍：墙、窗、横梁、栅栏、顶棚
- 码头：海平线、木桩、远船、栏杆
- 果园：树阵、风车、围栏、远山
- 集市：棚布、摊位骨架、旗帜、灯串

作用：

- 稳定方向感
- 填补远景和中景
- 降低“空荡感”

#### B. Interactive Anchor：交互锚点

真正和玩法强相关的对象。

例如：

- 鸡舍：料斗、食槽、小鸡、鸡蛋
- 码头：抛竿点、水花点、鱼桶
- 果园：果树、果筐、压榨桶、蜂箱
- 集市：公告板、摊位、订单提交点

原则：

- 位置要稳定
- 不要大范围随机
- 玩家应当逐渐记住它们的大致方位

#### C. Ambient Anchor：氛围锚点

不承担核心交互，但负责“场景活着”。

例如：

- 飘尘
- 羽毛
- 水波高光
- 树叶摇晃
- 灯笼轻摆
- 远处路人剪影

作用：

- 丰富视野
- 提供运动线索
- 降低静态背景感

#### D. Cue Anchor：引导锚点

用来把玩家视线从中间带到侧面。

例如：

- 侧面传来的鸡叫
- 集市边缘闪烁的小灯
- 果园侧边蜂箱嗡鸣
- 码头远侧的海鸥声和水花

这类对象比“再多放几个模型”更值。

---

### 2.3 不要做全随机大散点，要做“可控变化”

对这类生活化 3DoF 场景，最好的丰富方案不是纯随机铺满，而是：

```text
人工确定主结构
-> 给每个主结构挂一组规则簇
-> 在小范围内做 seed 变化
```

可以理解成：

#### 规则簇示例

1. **鸡舍规则簇**
   - 食槽附近：草屑 + 小脚印 + 偶发啄食动画
   - 鸡窝附近：羽毛 + 稀有蛋闪光
   - 窗边：日光束 + 漂尘

2. **码头规则簇**
   - 水花点附近：浮漂 + 环形波纹 + 海鸟叫
   - 木桩附近：绳结 + 小桶 + 渔网
   - 远船附近：雾感 + 慢速剪影

3. **果园规则簇**
   - 果树下：落果 + 草叶 + 小蜜蜂
   - 压榨桶附近：木箱 + 果渣 + 小木勺
   - 风车附近：缓慢旋转叶片 + 旗帜摆动

4. **集市规则簇**
   - 摊位前：木箱 + 布袋 + 木牌
   - 公告板周围：纸张摆动 + 小图钉 + 短提示
   - 灯串附近：暖光点 + 飘旗

这样做的好处：

- 玩家能记住场景逻辑
- 每次进入又不会完全一样
- 内容丰富度提升，但不会失控

---

### 2.4 最重要的布局原则：前弧区密，侧弧区巧，后弧区轻

建议每个场景按方位做权重分布：

#### 前方主弧区：`-60° ~ +60°`

放：

- 主交互对象
- 主视觉主体
- 当前局目标

占比建议：

- **60% ~ 70% 的信息量**

#### 侧方发现区：`60° ~ 100°` 与 `-60° ~ -100°`

放：

- 次交互对象
- 声音引导点
- 稍后才需要关注的目标

占比建议：

- **20% ~ 30%**

#### 后侧轻内容区：`|yaw| > 100°`

放：

- 纯氛围对象
- 少量隐藏发现
- 非关键声音来源

占比建议：

- **10% 左右**

原则：

- 后方可以有惊喜，但**不能放主任务流程**
- 让玩家愿意偶尔转头，而不是被迫频繁大幅转身

这和你文档中“正前方 ±90° 为主要交互区”的规则完全一致。

---

### 2.5 深度层次怎么做，才像空间而不是平面贴图

不论你当前还是 Canvas 伪 3D，还是后续切 Three.js，都建议统一做 4 层深度带：

#### Layer 1：Far / 远景层

作用：

- 建立场景环境
- 形成稳定地平线 / 背景

典型对象：

- 天空、远山、海平线、屋顶轮廓、远棚布

特点：

- 移动幅度最小
- 细节不需要多

#### Layer 2：Mid / 中景结构层

作用：

- 形成“这个地方是什么”的主要识别

典型对象：

- 树、窗、横梁、摊位、风车、远栅栏

特点：

- 占据主要画面结构
- 有少量动画即可

#### Layer 3：Near / 近景交互层

作用：

- 承担玩家真正要点的对象

典型对象：

- 小鸡、鸡蛋、料斗、食槽、水花点、蜂箱、公告板

特点：

- 命中判定明确
- 高亮、UI、音效都围绕这层展开

#### Layer 4：FX / 瞬时反馈层

作用：

- 给场景“生命感”和“手感”

典型对象：

- 爱心粒子
- 飘字
- 落叶
- 水波
- 亮点闪烁
- 漂尘

特点：

- 数量少但要有效
- 这些东西对“丰富感”的贡献往往大于再加几个静态模型

---

### 2.6 针对四个保留场景的具体摆放建议

#### 1. 鸡舍

目标感受：温暖、近距离、陪伴感强

建议：

- 主互动对象全部放在前方 `-70° ~ +70°`
- 左右侧各放一个“次发现点”，例如：
  - 左侧草堆里的鸡蛋
  - 右侧躲在边缘的小鸡
- 远景只保留：
  - 窗光
  - 顶梁
  - 墙面挂物
- 丰富度主要靠：
  - 小鸡轻移动
  - 漂尘
  - 草屑
  - 鸡叫的方向感

不建议：

- 再堆很多大型装饰
- 做太深的后方空间

#### 2. 码头

目标感受：开阔、可听声辨位、等待咬钩

建议：

- 远景重点是海平线和远船剪影
- 中景是栏杆、木桩、渔具
- 交互点集中在前弧区与一侧边弧区
- 让玩家通过：
  - 水花
  - 海鸟
  - 风声
  来判断新热点

丰富度来源不该是“满海面都摆东西”，而是：

- 局部可辨识的热点
- 水面动态
- 声音线索

#### 3. 果园

目标感受：层次多、摇树和收集很直观

建议：

- 树阵做成弧形包裹，不要只摆一排
- 前方主树 1 棵，中侧各 1 棵
- 地面保持少量落果和果筐
- 风车作为高处结构锚点
- 蜂箱可以作为侧向引导点

丰富度来源：

- 树冠大小错落
- 叶片轻摆
- 落果动画
- 蜜蜂或亮点轨迹

#### 4. 集市

目标感受：信息稍密，但依然清楚

建议：

- 公告板放在正前方中心偏近位置
- 左右摊位分担出售功能
- 棚布、灯串、旗帜负责中上部空间
- 侧边摊位用灯光和短音效引导转头

关键点：

- 集市最容易“太满太乱”
- 所以要控制色块和交互热点数量
- 一次只突出一个主任务对象

---

### 2.7 AI / Hugging Face 在这里最适合做什么

AI 布局不适合直接放到运行时做。

更适合的定位是：

#### 作为离线创作辅助

可以用来做：

1. **场景语义草图**
   先生成“鸡舍里什么该挨着什么”的布局想法。

2. **规则簇启发**
   例如：
   - 食槽附近应该有哪些陪衬物
   - 集市摊位周围哪些小物件最能增加生活感

3. **构图对照**
   验证“前弧区是否够丰富、侧弧区是否有发现点”

这和 Hugging Face 上的 3D 布局研究方向是吻合的。近两年的相关工作越来越强调：

- **布局是控制感的来源**
- **语义关系比纯随机散点更重要**

但对你当前项目来说，正确落地方式不是“运行时让 AI 摆场景”，而是：

```text
AI 给布局灵感
-> 人工确定主锚点
-> 代码做轻量 variation
```

## 3. 性能层面的配套建议

你这个问题表面上是“摆放”，实际上和性能强相关。移动端 3DoF 场景如果为了丰富度无脑加对象，很容易反噬到输入手感。

建议同步做三件事：

### 3.1 重复物件实例化

如果后续进入 Three.js 版本：

- 草屑
- 木箱
- 灯串
- 小旗
- 树叶
- 羽毛

这些重复物件应优先考虑 `InstancedMesh`。

原因：

- 它能明显减少 draw call
- 适合大量重复、低差异的小物件

注意：

- 如果动态修改实例矩阵，要记得更新 `needsUpdate`
- 实例位置变化后，必要时重新计算 bounding sphere / bounding box

### 3.2 距离分级

如果使用真实 3D 模型，建议对树、摊位、风车等结构物做 `LOD`：

- 近：完整模型
- 中：简化模型
- 远：平面化或更低模

并且给 LOD 切换加入轻微 hysteresis，避免边界闪烁。

### 3.3 声音数量控制

空间音频很重要，但不要贪多。

建议：

- 同时只保留 `1 ~ 3` 个强提示音源
- 其余环境音用非位置化环境底噪承担

这样既省 CPU，也避免玩家听觉负担太重。

## 5. 我对这两个问题的最终判断

### 对问题一

最适合你的不是“追求绝对精确的传感器系统”，而是：

**把不稳定输入包进一层稳定的体验设计里。**

也就是：

- 居中
- 死区
- 平滑
- 锁定
- 边缘提示
- 可拖动精调

玩家最终感受到的是“准不准”，不是“算法多高级”。

### 对问题二

最适合你的不是“做更大的 3D 场景”，而是：

**让每个定点观察场景都具备主结构、次发现点、氛围补充和声音引导。**

也就是：

- 主锚点稳定
- 丰富度靠层次和小变化
- 不靠满地图堆模型
- 不靠运行时 AI 乱生成
